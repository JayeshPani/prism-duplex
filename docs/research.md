## Actual FDB-v3 evaluation contract

1. The [upstream v3 README](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/README.md) describes 100 recordings, 79 scenarios, 12 speakers, four domains, and 12 tools. The [paper](https://arxiv.org/abs/2604.04847) evaluates disfluency, tool use, accuracy, latency and turn-taking. Neither a 10-item run nor a deterministic text replay establishes the full benchmark result.
2. [Binary pass-rate code](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/evaluate_pass_rate.py#L147): requires an exact multiset of function names and correct expected argument values; repeated functions are paired in recorded order. It does not check backend success, global dependency ordering, audible response, response correctness, or provenance of dynamic references. Exact matching lowercases, trims, replaces underscores with spaces, skips `$...` reference values, and ignores additional argument keys. GPT-4o semantic judging allows plausible reference values, aliases, date formatting and numeric tolerance; exceptions silently fall back to exact matching. The same file's CLI scans existing matching result files only, omitting absent files. Always report expected, attempted, produced, evaluated and excluded counts separately.
3. [Continuous scoring](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/evaluate_tool_calls.py#L344): separately scores function-name F1, argument correctness and optional GPT-4o response quality. Default aggregates include only samples with transcript or ASR chunks; `_all` tool metrics include all evaluated files. Its aggregate note claims no-response cases are scored zero, but the code actually computes their tool scores normally. Publish denominators and both aggregate variants; do not optimize toward silence or acknowledgments.
4. [Core runner](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/run_tool_benchmark.py#L279): evaluation ASR is NeMo `nvidia/parakeet-tdt-0.6b-v2`, with `.cuda()`. Input speech-end is the end before the first word gap exceeding two seconds, else the last word end. Output ASR supplies words/timestamps. Telemetry comes from `/tmp/agent_tool_calls.log`, filtered by room and rebased to stream start. These files and the original room identifiers must be preserved; stale/failed/duplicate dispatches belong in the record. The `--asr-only` code creates a fresh result and does not restore room/stream metadata before telemetry extraction, so treat rescoring as a separate copied-artifact operation and verify metadata retention.
5. [LiveKit audio client](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/livekit_inference.py#L140) uses a fixed output buffer with the input recording duration. Do not lengthen recording, edit silence, or drop calls without declaring an adapted run. The batch runner merges per-folder metadata for inference bookkeeping; evaluators load the specified benchmark JSON independently. Metadata is not an agent prompt.
6. [Latency analyzer](https://github.com/DanielLin94144/Full-Duplex-Bench/blob/3e799c45a045256f47d5f1c9cda90157e2d2ec9e/v3/analyze_tool_latency.py#L121): first response = first output word minus inferred user end (includes acknowledgments); first tool = first list entry's start minus user end; task latency = GPT-4o-selected substantive-answer start minus user end. It does not measure final effect completion or audible stop after barge-in. Aggregates exclude silent and negative-first-response samples, report median/mean but no p95. Add separate clearly named development metrics rather than changing official semantics.

Executed stdlib-only probes against the pinned scorer: correct tool with silence **passes**; correct tool with `status:error` result **passes**; extra argument **passes**; arbitrary dynamic-reference ID **passes**; extra duplicate tool **fails**; wrong literal **fails**. Raw results: `results/reliability/fdb-contract-probes.json`. Reproduce with `.venv/bin/python scripts/probe_fdb_contract.py bench/Full-Duplex-Bench/v3 --out results/reliability/contract-rerun.json`. These demonstrate scorer scope, not PRISM performance.

## Mac ASR adaptation and reproducibility

[MLX model card](https://huggingface.co/mlx-community/parakeet-tdt-0.6b-v2) says it is a conversion of [NVIDIA Parakeet v2](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2). That establishes lineage, not identical decoding or timing. `scripts/fdb_infer.py` replaces both input and output evaluation ASR and reconstructs words from token-leading spaces. Differences can change inferred user end, take-turn detection, transcript judged response quality and latency. Binary tool pass-rate ignores ASR, but that does not make the complete result directly comparable. Label runs “FDB-v3 adapted: MLX evaluation ASR”; record both model revision and `parakeet-mlx` version. Keep the actual agent STT backend separate from the post-hoc evaluation ASR in manifests.

Comparability experiment: freeze a set of development WAVs with disfluencies, numbers, silence and overlap; decode identical files in NeMo/CUDA and MLX; compare token/word errors, first/last word and >2s gap decisions, take-turn changes and latency deltas. For an already frozen benchmark audio output, a later independent scoring comparison may be reported, but must not feed item-level information into prompts or tuning. Do not claim parity until measured.

A seed is not proof of determinism. `JUDGE=none` is an exact fallback, not uniformly stricter than semantic judging because it skips references and extra keys. `JUDGE=local`/`kimi` modifies judge model and token budget, so must be separated. GPT-4o in upstream is a model alias rather than immutable model snapshot; save returned model ID and requests/responses if used.

## Prioritized research with experiments

### 1. Operation identity and truthful outcomes — highest engineering value

**Primary source:** AWS [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). Published engineering evidence: identical parameters can represent different intentions; caller operation identifiers distinguish retries, and token recording plus mutation must be atomic to obtain the backend guarantee. A missing reply leaves the client uncertain.

**PRISM hypothesis:** scoping retry identity to an intentional action, with explicit failed/unknown states, fixes legitimate repeated visits without inventing exactly-once effects. Effort small for in-process identity and outcomes, larger for durable backend reconciliation. Risk: new IDs on retries duplicate effects, reused IDs on new intents suppress useful requests. Test same-operation concurrent submission, same-args new action after another destination, known error then retry, timeout after effect before acknowledgment, and restart. Claim process-local duplicate control only unless the backend atomically supports durable identities. No new research novelty claim; this is established engineering applied to voice.

### 2. Endpointing, barge-in and speech cancellation — measure before tuning

**Primary source:** current [LiveKit turn handling docs](https://docs.livekit.io/agents/logic/turns/) distinguish VAD/semantic endpointing, true interruptions and empty-transcript false interruptions; they document resuming speech after false triggers. The live docs may differ from PRISM's pinned 1.8.3 API. Some current defaults/features use LiveKit inference, so blindly enabling them would violate local-inference requirements.

**PRISM hypothesis:** cancellation at detected speech onset plus version checks before dispatch and spoken output should bound obsolete work, while a measured false-interruption policy avoids dropping useful speech. Effort medium; risk is microphone echo stopping the agent or an interruption clearing valid in-flight work. Create independent prerecorded user tracks and local TTS output with cough/noise/backchannel/correction variants; record both channels at the listener, and measure stop latency, false stops, resumed speech and correction success. Unit events are useful but do not verify audible stopping. Retain the fixed policy until an adaptive variant improves correction/task accuracy without suppressing requests or violating a prespecified latency limit.

### 3. Incremental recognition and stable prefixes — promising, not implemented

**Primary source:** Macháček et al., [Turning Whisper into Real-Time Transcription System, v2](https://arxiv.org/abs/2307.14743v2), reports a local-agreement policy with self-adaptive latency; its 3.3-second long-form result is not a PRISM latency estimate. NVIDIA's model card describes Parakeet v2 as full-attention offline ASR. PRISM baseline explicitly sets `streaming=False, interim_results=False`; completed VAD segments and re-transcription are not true partial ASR.

**PRISM hypothesis:** stable-prefix incremental ASR can start reversible planning earlier, but final tool dispatch must wait for validated intent. Effort medium/high, risk changed prefixes deleting identifiers or eager dispatch preceding a correction. Compare final-segment baseline against stable-prefix partials on development audio. Measure partial revision rate, identifier accuracy, extra recognition compute/memory and end-to-substantive-response p50/p95. Keep earlier planning separate from earlier writes. Local agreement does not itself establish semantic completion.

### 4. Native duplex model alternative — research comparison, not immediate replacement

**Primary sources:** Défossez et al., [Moshi](https://arxiv.org/abs/2410.00037) and [official implementation](https://github.com/kyutai-labs/moshi). The paper models separate user/system streams and reports 200ms practical model latency; that is not tool-use completion or a measurement on this M2 Pro. Official code includes MLX.

**PRISM hypothesis:** a native speech front end may improve prosodic turn-taking, but tool reliability, integration cost and shared-memory pressure may worsen. Effort high; benchmark a small independent overlap/interrupt suite with the same tool contract, local execution and truthful action ledger before considering migration. Preserve the cascaded baseline. Replacing the architecture solely on a latency claim is not justified. Novelty would require controlled evidence beyond combining known components.

## Measurement plan and stop conditions

Use human-annotated audio event boundaries on a shared clock for live metrics. Record acoustic user speech end, STT final/partial, intent/version, planned/committed, backend dispatch/ack, speech synthesis start, listener's first acknowledgment audio, listener's first substantive audio, listener's final substantive audio, detected user interruption and last audible assistant sample. Server `speak` invocation is not audible onset. Backend return is not spoken completion. Clock sync/recording alignment error should be reported.

Report separately: acknowledgment latency, speech-end to substantive response, speech-end to tool dispatch, effect completion, interruption-onset to audible stop, correction success, completed-task accuracy, stale dispatches, duplicate effects, legitimate repeat success and unnecessary clarification. Include timeout/no-response counts rather than assigning them zero latency. Compute p50/p95 on a declared sample set, plus negative/early-speaking counts; do not report a small sample's p95 as stable. Report all calls even when effects are cancelled or unknown.

Ablate one factor at a time: fixed versus adaptive commitment; corrected action identities versus old argument hash; acknowledgments on/off; then local model size. Use independent development recordings and frozen seeds/configs, run the same recordings in each cell, retain raw traces/audio and report task success alongside latency. Under 1/2/4 rooms measure queue wait, STT/LLM/TTS overlap, peak process memory/system pressure and response p95. The baseline shares a serialized STT engine across rooms, so per-room state isolation does not imply latency isolation.

Target hardware: Apple M2 Pro, 16GB, Python 3.11.13. Later [iteration evidence](iteration2.md) includes actual local TTS/STT, four Qwen navigation cases, 24 text development scenarios, and a 1/2/4-room component-overlap probe. It does not establish microphone echo handling, recognition during playback, audible barge-in, sustained room capacity, or a full-audio benchmark result. Model snapshots are now available. LiveKit Cloud credentials and local benchmark audio are absent, but Cloud access is not a requirement: [LiveKit supports a local development server](https://docs.livekit.io/transport/self-hosting/local/), and the upstream benchmark archive landing page is publicly reachable. Neither local transport nor archive transfer has been tested here. See [iteration 3](iteration3.md) for capture limitations. With transport and data configured, use `PRISM_PROFILE=local-mac JUDGE=none LIMIT=10 bash scripts/run_benchmark.sh` for an explicitly adapted smoke run; freeze a config before the full run without LIMIT. For comparable official ASR use a CUDA host with `PRISM_PROFILE=local-cuda JUDGE=openai bash scripts/run_benchmark.sh`, recording the hosted judge separately from fully local agent inference and audio transport. Preserve prior artifacts; never replace benchmark failures with reruns in a purported untouched holdout.

## Retained implementation after the audit

Installed LiveKit Agents **1.8.3** source confirmed that automatic turn/interruption settings can select hosted inference. The revised entrypoint explicitly sets VAD turn detection and VAD interruption mode, preserving local Silero inference in dev and production. Tentative VAD events do not programmatically destroy playback; a finalized new transcript interrupts stale handles. These are source/config tests, not measured acoustic cancellation.

A race between the gate task and scheduled commit could clear the original pending request before the commit recorded history. Pending/history transfer is now performed together after the commit's intent-version check, covered by an independent test. The old one-per-room latency shortcut mixed old tool timestamps with current acknowledgments; it was removed. Speech-handle events and queued response kinds remain explicit server-side evidence, while acoustic onset/stop metrics remain unmeasured.
